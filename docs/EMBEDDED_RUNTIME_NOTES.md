# Вбудований Wine: пакування та умови випуску

Дослідження від **5 вересня 2026 року**. Це проєктні нотатки й аудит початкового пакування, а не підтвердження запуску ігор, прийняття до Mac App Store або повного виконання умов ліцензій. Збірки, запуск Wine і зміна налаштувань захисту macOS у межах цього дослідження не виконувалися.

## Що можна вбудувати

Кандидат для локального прототипу — вже завантажений `wine-stable-11.0_1-osx64.tar.xz`: 185 303 032 байти, SHA-256 `b50dc50ec7f41d58b115a6b685d4d1315ba3c797bd3aa0f49213f2703cb82388`. Версія стосується пакування Gcenx; базовий Wine — 11.0. Випуск містить Wine Gecko 2.47.4 і Wine Mono 10.4.1 та потребує системного GStreamer.framework. [Випуск](https://github.com/Gcenx/macOS_Wine_builds/releases/tag/11.0_1), [метадані випуску](https://api.github.com/repos/Gcenx/macOS_Wine_builds/releases/tags/11.0_1).

Для початкового розміщення підходить **повне** дерево `Wine Stable.app/Contents/Resources/wine`, а не два окремі файли:

```text
Portico.app/Contents/Frameworks/WineRuntime/
  bin/wine
  bin/wineserver
  lib/…                 # Unix-бібліотеки й Windows-модулі обох архітектур
  share/wine/…          # wine.inf, Mono, Gecko та інші дані
```

Це проєктна схема. Саме перенесення не доводить автономність і придатність структури для фінального підпису. Wine 11 визначає `bin` і `share/wine` відносно завантаженого `ntdll.so`; збереження відносної структури має підставу у вихідному коді. Окремо потрібно перевірити всі Mach-O install names, `rpath`, символічні посилання, динамічно відкривані бібліотеки та шляхи ресурсів. [Wine 11: `init_paths` у loader.c](https://github.com/wine-mirror/wine/blob/wine-11.0/dlls/ntdll/unix/loader.c).

У початковому Portico вже задано `DistributionPolicy.bundledWineURL` із цим шляхом. На момент дослідження `WineEngine` задавав `WINEPREFIX`, `WINELOADER`, `WINESERVER` і `PATH`, але не середовище приватного GStreamer; простий вибір шляху до Wine цього не вирішує. Після подальших змін коду цей знімок слід перевіряти повторно.

## Залежності та перенесення GStreamer

README пакувальника називає MacPorts/macports-wine джерелами залежностей, а freetype, GStreamer, GnuTLS, libinotify, SDL2 і MoltenVK — залежностями runtime. Прапорці configure містять `--with-ffmpeg`, `--with-vulkan`, `--without-opengl` і `--enable-archs=i386,x86_64`. Вони не є обіцянкою DirectX 11/12 або підтвердженням фактичного складу кожного бінарного файлу. [Закріплений README 11.0_1](https://github.com/Gcenx/macOS_Wine_builds/blob/11.0_1/README.md).

Офіційна документація GStreamer описує приватний framework у `Contents/Frameworks`, перенесення бібліотек і налаштування `GST_PLUGIN_SYSTEM_PATH`, `GST_PLUGIN_SCANNER`, `GIO_EXTRA_MODULES`. Її приклад давній і розрахований на основний executable у `Contents/MacOS`: шлях `@executable_path/../Frameworks/…` не можна механічно переносити на Wine, який запускає різні дочірні executables. Потрібно обчислити шляхи для фактичних завантажувачів, сканера плагінів і всіх транзитивних бібліотек, а потім підписати змінені Mach-O. [Приватне розгортання та перенесення GStreamer](https://gstreamer.freedesktop.org/documentation/deploying/mac-osx.html).

Встановлення GStreamer у `/Library/Frameworks` може бути проміжною залежністю локальної розробки; такий результат не можна називати автономним вбудованим рушієм. Перевірка автономності має відбуватися на Mac без зовнішнього GStreamer/MacPorts/Homebrew. Додавання всього framework без інвентаризації плагінів також не є завершеним аудитом ліцензій.

## Ліцензії та точні вихідні коди

Wine дозволяє розповсюдження та зміни за **LGPL 2.1 або пізнішою версією**. З цього не випливає обов'язок самостійно компілювати кожен бінарний файл, який розповсюджується. Однак розповсюджувач готової збірки відповідає за застосовні умови так само, як початковий пакувальник. Власний сертифікат підтверджує постачальника конкретного пакування й не замінює цих зобов'язань. [Wine LICENSE](https://github.com/wine-mirror/wine/blob/wine-11.0/LICENSE).

Практичні вимоги LGPL 2.1 для планування випуску:

- Зберегти повідомлення про авторські права, відсутність гарантії й текст ліцензії; позначити власні зміни та дати.
- Для розповсюдження Wine у бінарній формі забезпечити повні відповідні вихідні коди за §4, включно з використаними build/install scripts із визначення §0. Якщо бінарні файли завантажуються з певного місця, §4 передбачає еквівалентний доступ до вихідного коду звідти ж. Загальне посилання на поточний Wine не встановлює відповідності конкретній збірці.
- Якщо компонування з LGPL-бібліотекою підпадає під §6, вибрати застосовний спосіб надання матеріалів для перекомпонування й зберегти передбачені права користувача на власні зміни та їх налагодження. Наявність `.dylib` сама собою не доводить виконання §6(b).
- Окремо оцінити архітектуру незалежного лаунчера: проста агрегація за §2 не переводить увесь самостійний інтерфейс під LGPL автоматично. Це не звільняє Wine та його залежності від власних умов.

Першоджерело: [Wine COPYING.LIB, LGPL 2.1](https://raw.githubusercontent.com/wine-mirror/wine/wine-11.0/COPYING.LIB). Для приватної локальної розробки великі архіви вихідного коду на цьому етапі не завантажувалися; перед передаванням бінарної збірки іншим людям питання розповсюдження потребує перевірки.

GStreamer не має однієї ліцензії на весь пакет: його LGPL-плагіни можуть залежати від бібліотек з іншими умовами, включно з GPL; існують окремі питання прав на кодеки. Потрібні точні версії та склад фактично включених модулів, тексти ліцензій і повідомлень та відповідні вихідні коди там, де вони потрібні. Wine Mono і Wine Gecko також мають власний склад та умови. [Ліцензування GStreamer](https://gstreamer.freedesktop.org/documentation/frequently-asked-questions/licensing.html), [Юридичні питання GStreamer](https://gstreamer.freedesktop.org/documentation/frequently-asked-questions/legal.html), [Wine Mono 10.4.1](https://github.com/wine-mono/wine-mono/tree/wine-mono-10.4.1).

## Зібрані матеріали та перешкоди для публічного випуску

У `config/runtime-licenses` збережено без змін Wine 11.0 `LICENSE`, `COPYING.LIB`, `AUTHORS`, README пакувальника 11.0_1 і невеликі JSON-метадані його дерева та випуску. `SOURCES.json` містить первинні URL, розміри й SHA-256 отриманих файлів. Це **початковий комплект повідомлень, а не повний corresponding source**.

У перевіреному tag `11.0_1` (`362fe0e69deeced7ac4db06e1ff69652569313b2`) репозиторію пакувальника є README та кілька службових файлів, а не повні вихідні коди Wine із залежностями й відтворюваний build manifest. Пошук імен LICENSE/COPYING/COPYRIGHT/NOTICE/README у завантаженому bundle не знайшов документів; це обмежений пошук за іменами, а не доказ відсутності всіх можливих повідомлень. [Дерево закріпленого tag](https://api.github.com/repos/Gcenx/macOS_Wine_builds/git/trees/11.0_1?recursive=1).

До публічного постачання залишаються:

1. Встановити точні вихідні коди Wine, патчі пакувальника, build/install/relocation scripts, версії та походження всіх включених залежностей. Якщо відповідність вихідних кодів артефакту Gcenx встановити неможливо, зібрати власний runtime із зафіксованих джерел.
2. Підготувати повний набір ліцензій і повідомлень, канал надання відповідних вихідних кодів та manifest, який можна перевірити. Окремо перевірити Gecko/Mono/GStreamer/кодеки й сумісність користувацьких умов постачання з їхніми ліцензіями.
3. Завершити перенесення та перевірку автономності; перевірити Windows-застосунок, звук і відео, вікна, введення, створення середовища й завершення всіх дочірніх процесів. Успіху `wine --version` недостатньо.
4. Для прямого випуску підписати кожну вкладену одиницю коду з належними параметрами, потім підписати Portico й пройти notarization та перевірку Gatekeeper. Для MAS окремо підготувати sandbox, helpers, файлові дозволи та збірку для подання.

Apple описує ручний підпис для зовнішньої системи збірки й радить уникати `codesign --deep` як способу підписання складного продукту: різні виконувані файли можуть потребувати різних entitlements. Зміна install names виконується **до** фінальних підписів. Локальний ad-hoc підпис — етап розробки, а не Developer ID, notarization або схвалення App Store. [Створення коду з підписом для розповсюдження](https://developer.apple.com/documentation/xcode/creating-distribution-signed-code-for-the-mac/), [Нотаризація програм для macOS](https://developer.apple.com/documentation/security/notarizing-macos-software-before-distribution).

Невдалу системну оцінку початкового архіву не виправляє саме переміщення в bundle. План вбудовування не передбачає вимкнення Gatekeeper, видалення quarantine для обходу перевірки або широкого вимкнення library validation. Наявність вбудованого runtime також не вирішує вимоги [Mac App Store](APP_STORE.md).
